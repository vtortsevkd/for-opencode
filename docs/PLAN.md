# План реализации: укрепление пайплайна FIS-агента (JavaScript)

> **Кому:** агенту-исполнителю.
> **Что это:** план достройки 5 модулей поверх уже работающего пайплайна.
> **Стек:** JavaScript (Node.js).
> **Главное правило:** это brownfield-изменение. Добавляй слои **вокруг** существующего
> конвейера, не переписывай этапы. Существующий пайплайн должен продолжать работать.

---

## 0. Текущее состояние (НЕ трогать, только учитывать)

Уже реализовано и работает:

- Пайплайн разбивает задачу на этапы, каждый этап генерирует один артефакт.
- **Каждый этап — отдельный субагент.** Артефакты всегда пишутся в файлы.
- Между этапами стоят гейты; есть «атаки» на реализацию и «судьи», выносящие вердикт.
- REST-доступ к платформе FIS вынесен в отдельные tools, агент пользуется ими.
- Существует `agent.md`.
- Подключены MCP: Pyrus, Confluence, YouTrack (Grafana появится позже — в этой работе не используется).

**Что НЕ входит в эту работу (намеренно пропущено):**

- Модуль 7 — «Grafana как петля обратной связи» — отложен, не делать.

## 0.2 Соглашения для JavaScript (реализация)

### Принципы

- **Zero-dependency по умолчанию.** Используй встроенные модули: `node:fs/promises`,
  `node:path`, `node:crypto`, `node:test`. Новые npm-зависимости — только если они уже
  есть в проекте и без них нельзя.
- **Данные** — JSON / JSONL (NDJSON). Одна запись = одна строка в JSONL.
- **Идентификаторы и имена файлов/полей** — на английском (kebab_case / snake_case).
- **Иммутабельность** — функции не мутируют входные объекты, возвращают новые.
- **Журнал решений — append-only** (см. модуль 5).

### Предлагаемая структура новых файлов (адаптируй под фактическую)

```
lib/pipeline/
  config.js            # пути, maxAttemptsPerStage, stallThreshold
  metrics.js           # record(event), aggregateReport()
  ledger.js            # appendDecision(), decisionsFor()
  recovery.js          # diagnoseFailure(), recover(), stallDetector()
  judges/
    registry.js        # маппинг "тип артефакта -> градеры", grade()
    code.js            # детерминированные code-градеры
    rule.js            # rule-градеры (schema / regex)
    llm.js             # LLM-судья (только явно)
  memory/
    instincts.js       # load(), reflect(), inject()

metrics/               # NDJSON-логи прогонов
  <task_family>/run-<run_id>.jsonl
memory/
  instincts.json       # извлечённые правила
<task_dir>/decisions.jsonl   # журнал решений на задачу
```

## Модуль 1 — Метрики пайплайна (pass@k и стоимость)

### Цель
Сделать конвейер измеримым: на каждый прогон задачи собираются события, по которым
можно посчитать `pass@1`, `pass@3`, время и число повторов. Без этого нельзя понять,
улучшается ли пайплайн.

### Что построить

1. **Эмиттер метрик** — `record(event)` из `lib/pipeline/metrics.js`, дописывает одну
   JSONL-строку в файл текущего прогона. Вызывается из пайплайна, не руками.

2. **Точки эмиссии** (встроить в существующий поток):
   - старт задачи
   - старт и конец каждого этапа
   - каждый вердикт гейта / судьи / атаки (pass или fail)
   - каждый повтор (attempt) генерации артефакта на этапе
   - финальный статус задачи (`done` / `failed` / `escalated`)

3. **Агрегатор** — `aggregateReport()` читает логи метрик и печатает/возвращает отчёт.

### Формат записи (одна JSONL-строка)

```json
{
  "task_family": "crud",
  "task_id": "task-2026-001",
  "run_id": "run-8f3a",
  "ts": "2026-11-25T10:12:33Z",
  "event": "stage_end",
  "stage": "implement",
  "outcome": "pass",
  "attempt_number": 1,
  "duration_ms": 8120,
  "tokens_used": null
}
```

Поля:
- `task_family` — категория задачи (например `crud`, `search`, `ui`); используется для группировки.
- `event` — тип события (`task_start`, `stage_start`, `stage_end`, `gate`, `judge`, `attack`, `attempt`, `task_end`).
- `outcome` — `pass` / `fail` / `escalated` (для событий, где применимо).
- `attempt_number` — номер попытки генерации артефакта на этом этапе (начинается с 1).
- `duration_ms` — длительность, если известна.
- `tokens_used` — если у харнесса есть доступ к использованию токенов; иначе `null`.

### Определения метрик (зафиксировать однозначно)

- **attempt** = повторная генерация артефакта на одном этапе после отрицательного
  вердикта (гейт/судья/атака). Первая генерация = `attempt_number: 1`.
- **pass@1** = доля задач, завершённых со статусом `done`, у которых **ни один этап**
  не потребовал повтора (все этапы прошли с `attempt_number: 1`).
- **pass@3** = доля задач `done`, у которых суммарное число attempts по всем этапам `<= 3`.
- **стоимость задачи** = суммарное `duration_ms` (и `tokens_used`, если доступно) + число attempts.

### Выход агрегатора

Отчёт по каждой `task_family`:
- всего задач, `done`/`failed`/`escalated`
- `pass@1`, `pass@3` (в %)
- среднее время на задачу, среднее число attempts
- **топ этапов по числу fail** — какой этап чаще всего валится

### Acceptance criteria
- [ ] Каждый завершённый прогон оставляет минимум события `task_start` и `task_end`.
- [ ] Запись метрик не требует ручного вмешательства (встроена в пайплайн).
- [ ] `aggregateReport()` выдаёт таблицу `pass@1`/`pass@3`/среднее время по `task_family`.
- [ ] Прогон тестовой задачи оставляет корректный NDJSON-файл (проверить парсингом).

## Модуль 2 — Гибридные судьи

### Цель
LLM-судья — самый флаки-источник. Заменить его на детерминированные проверки везде,
где критерий можно проверить кодом или правилом. LLM остаётся только для семантически
открытых артефактов.

### Что построить

1. **Единый контракт судьи.** `grade()` возвращает структурированный вердикт:

```json
{
  "verdict": "pass",
  "checks": [
    { "name": "object_read_back", "type": "code", "result": "pass", "detail": "объект прочитан обратно" }
  ]
}
```

`verdict` ∈ `pass` | `fail` | `review`. `checks` — обязательный список проверок, не свободный текст.

2. **Три типа градеров:**

| Тип | Как проверяет | Пример для FIS |
|-----|---------------|----------------|
| `code` | вызывает детерминированную функцию проверки | REST verify-чтение созданного объекта; поисковая функция вернула ожидаемое число записей |
| `rule` | regex / JSON Schema / валидация обязательных полей | артефакт валиден по схеме; нет запрещённых имён полей |
| `llm` | модель | только семантические критерии без детерминированного аналога |

3. **Правило маршрутизации:** приоритет `code` → `rule` → `llm`. LLM-судья вызывается
   **только** если для артефакта явно не задан детерминированный градер.

4. **Реестр судей** — `registry` в `judges/registry.js`: маппинг «тип артефакта → список градеров».
   Ключи — типы артефактов, реально используемые в пайплайне (уточни по факту).

### Acceptance criteria
- [ ] Реализовано минимум 2 `code`-градера для типичных FIS-артефактов (например
      CRUD-объект и результат поисковой функции).
- [ ] `grade()` возвращает структурированный вердикт с `checks`, а не свободный текст.
- [ ] LLM-судья вызывается только по явной конфигурации, когда детерминированной проверки нет.
- [ ] Существующие вызовы судей в пайплайне переведены на новый контракт без потери вердиктов.

## Модуль 3 — Память и обучение между запусками

### Цель
После каждой завершённой задачи извлекать одно атомарное правило («инстинкт»), которое
впрыскивается в следующие прогоны. Пайплайн должен становиться умнее с каждым прогоном.

### Что построить

1. **Хранилище правил** — `memory/instincts.json` (массив записей):

```json
{
  "id": "INS-001",
  "pattern": "агент создал объект, но не прочитал его обратно",
  "signal": "crud_create_without_verify_read",
  "rule": "после create всегда выполнять verify-чтение, иначе этап не считается закрытым",
  "source_task_id": "task-2026-001",
  "added_at": "2026-11-25T10:30:00Z",
  "hit_count": 1
}
```

2. **Шаг извлечения (reflection)** — `reflect(taskDir, meta)` из `memory/instincts.js`.
   После финального гейта задачи читает журнал решений (модуль 5) + вердикты судей и:
   - извлекает **0 или 1** новое правило (не больше одного за задачу);
   - проверяет по `signal`, нет ли уже похожего правила (дедупликация);
   - если нового нет — явно фиксирует «ничего нового» (запись в журнал, без добавления).

3. **Точка впрыскивания** — `inject(taskFamily)`. На старте следующего прогона возвращает
   релевантные правила из `memory/instincts.json`; они добавляются в контекст агента
   (в `agent.md` или в брифинг соответствующего этапа). Релевантность — по `task_family`
   или по совпадению `signal` с типом выполняемой операции.

### Acceptance criteria
- [ ] После каждой задачи есть шаг, который либо добавляет правило, либо явно пишет «ничего нового».
- [ ] Правила из памяти появляются в контексте следующего прогона.
- [ ] Дедупликация по `signal` предотвращает дубликаты.
- [ ] `hit_count` увеличивается, когда правило реально предотвратило ошибку (опционально, но желательно).

## Модуль 5 — Append-only журнал решений

### Цель
Фиксировать решения между этапами, чтобы судья на этапе N видел **почему** приняты
решения на этапах 1..N-1, а агент мог возобновить задачу с середины без потери контекста.

### Что построить

1. **Файл журнала на задачу** — `<task_dir>/decisions.jsonl` (JSONL, append-only).
   `appendDecision()` в `ledger.js` — только дописывает в конец.

2. **Формат записи:**

```json
{
  "id": "D-003",
  "stage": 2,
  "gate": "schema_review",
  "decision": "выбрана схема объекта X",
  "reason": "поле Y обязательное (Confluence §Z)",
  "alternatives": ["X'", "X''"],
  "rejected_reason": "X' не поддерживает поле Y; X'' несовместимо с реестром",
  "by": "agent",
  "ts": "2026-11-25T10:15:00Z"
}
```

3. **Правила журнала:**
   - **Append-only**: `appendDecision()` открывает файл в режиме `'a'` и только дописывает.
     Переписывание/редактирование старых записей запрещено. Любая попытка изменить
     историю — это ошибка, не молча.
   - Запись создаётся на **каждом** гейте и на каждом значимом решении этапа.
   - Судья на этапе N получает записи этапов 1..N-1 как часть своего контекста
     (через `decisionsFor()`).

### Acceptance criteria
- [ ] После каждого гейта в журнале есть запись.
- [ ] Журнал монотонно растёт; старые записи не редактируются.
- [ ] Судья получает цепочку решений, а не только артефакт.
- [ ] Есть защита от переписывания (минимум — режим `'a'` + конвенция; желательно — хэш-цепочка
      или git-коммит на закрытие задачи).

## Модуль 6 — Протокол восстановления вместо ретрая

### Цель
При сбое этапа — **диагноз → точечная починка → запись**, а не слепой повтор. Плюс
детектор застревания, чтобы пайплайн не крутил бесконечную петлю «генерация → fail → генерация».

### Что построить

1. **Диагноз** — `diagnoseFailure(fail)` из `recovery.js`. Когда этап получает `fail`
   (гейт/судья/атака), перед повтором классифицирует причину по ограниченному набору:

```
schema_mismatch   — неверная структура/поля артефакта
missing_verify    — не выполнена обязательная проверка (например, verify-чтение)
invalid_input     — невалидные входные данные этапа
judge_flake       — детерминированная проверка прошла, но LLM-судья дал fail
unknown           — причина не определена
```

2. **Contained recovery** — `recover(artifact, failureClass)`. Повторная генерация
   исправляет **только** сломанный артефакт (один файл/артефакт). Затрагивать другие
   артефакты запрещено. Причина фиксируется в записи повтора.

3. **Introspection report.** После каждого восстановления в журнал (модуль 5) пишется запись:

```json
{
  "id": "R-002",
  "type": "recovery",
  "stage": 3,
  "failure_class": "missing_verify",
  "what_failed": "объект создан без обратного чтения",
  "what_fixed": "добавлен verify-чтение перед закрытием этапа",
  "prevention": "добавлено правило INS-001"
}
```

4. **Детектор застревания** — `stallDetector(taskDir, stage, fail)` из `recovery.js`.
   Конфигурируемые пороги в `config.js`:
   - `maxAttemptsPerStage` (default `3`) — максимум повторов одного артефакта на этапе.
   - `stallThreshold` (default `3`) — одинаковый `fail` подряд (тот же класс причины, тот же артефакт).
   При достижении порога: **не ретраить**, а сменить стратегию — эскалировать человеку
   (`outcome: escalated`) или переформулировать подзадачу. Поведение эскалации описать в отчёте.

### Acceptance criteria
- [ ] Fail этапа не ведёт к бесконечному ретраю.
- [ ] После каждого fail есть запись с `failure_class` и тем, что сделано.
- [ ] При застревании пайплайн останавливается и эскалирует, а не крутит петлю.
- [ ] `maxAttemptsPerStage` и `stallThreshold` настраиваются через `config.js`.
